# HyperFleet v0.2.0 → v1.0.0 Upgrade Guide

Migration guidance for operators and API consumers. For the per-item evidence checklist, see [v1.0.0 Breaking-Change Checklist](./v1.0.0/breaking-changes.md).

> **v1.0.0 requires a fresh database.** The upgrade is a **tear-down-and-redeploy**, not an in-place migration.

**See also:** [Release Process](./hyperfleet-release-process.md) · [API Versioning](../../components/api-service/api-versioning.md)

## Upgrade Procedure

All components - API, Sentinel, **and all adapters** - must be upgraded together. A partial upgrade fails: v0.2.0 API rejects PUT on `/statuses`; v1.0.0 API rejects POST. v0.2.0 adapters do not report `Finalized`, causing deletion flows to hang.

1. **Prepare v1.0.0 configuration** - apply changes from [§1](#1-configuration).
2. **Export v0.2.0 resource inventory** - query the v0.2.0 API before tear-down. **Use `pageSize` (the v0.2.0 parameter name), not `size` (v1.0.0 name).**

    ```bash
    curl -sf "${API_URL}/api/hyperfleet/v1/clusters?pageSize=1000" > clusters.json
    curl -sf "${API_URL}/api/hyperfleet/v1/clusters/{id}/nodepools?pageSize=1000" > nodepools-{id}.json
    # Repeat for each cluster ID. Also export any WifConfig, Channel, Version resources if applicable.
    # IMPORTANT: v0.2.0 uses `pageSize`, not `size`. Using the v1.0.0 param name
    # against the v0.2.0 API silently falls back to default page size (~20 items),
    # truncating your export.
    # -f (--fail) ensures curl exits non-zero on HTTP errors (e.g. 401) instead
    # of silently writing an error response body to disk.
    ```

3. **Audit DELETE call sites** - v0.2.0 DELETE returned `501 Not Implemented`; v1.0.0 returns `202 Accepted` with cascade ([§2.4](#24-delete-returns-202-accepted)). Code that ignored 501 will now trigger real deletions, including cascade-delete of child resources.
4. **Tear down v0.2.0** - stop all components.
5. **Provision fresh database** - do not reuse v0.2.0 database ([§4.1](#41-fresh-database)).
6. **Configure JWT authentication** - JWT is the only auth mechanism ([§1.3](#13-jwt-authentication-required), [§1.12](#112-ocm-sdk-removed)). **Production deployments must set `jwt.enabled: true` and configure at least one issuer under `configs`**. Setting `jwt.enabled: true` with an empty `configs: []` crashes the API at startup. Add separate issuers when external clients and in-cluster components use different token sources (e.g., one for GCP/ROSA gateway, one for K8s SA tokens). Sentinel and adapters also need service account tokens ([§1.14](#114-sentinel-and-adapter-api-client-jwt-authentication)).
7. **Deploy all v1.0.0 components** - API first (initializes schema on the fresh DB), then Sentinel, then adapters.
8. **Re-register resources** - create clusters, node pools via the API using inventory from step 2.
9. **Verify** - run [Post-Upgrade Verification](#post-upgrade-verification).

## 1. Configuration

### 1.1 Tracing environment variable renamed

**BREAKING.**

**Action required:** Replace `HYPERFLEET_LOGGING_OTEL_ENABLED` with `HYPERFLEET_TRACING_ENABLED` in deployment manifests or scripts.

`HYPERFLEET_LOGGING_OTEL_ENABLED` (v0.2.0) → `HYPERFLEET_TRACING_ENABLED` (v1.0.0). Old var is deprecated and ignored. Helm default remains `false`.

```bash
# v0.2.0 (no longer recognized)
HYPERFLEET_LOGGING_OTEL_ENABLED=true

# v1.0.0
HYPERFLEET_TRACING_ENABLED=true   # or =false to disable
```

> **If you don't act:** `HYPERFLEET_LOGGING_OTEL_ENABLED` is silently ignored. Tracing reverts to Helm default (`false`).

See [Tracing Standard](../../standards/tracing.md).

---

### 1.2 Sentinel message decision CEL configuration

**BREAKING.**

Decision logic moved from hardcoded Go (v0.2.0) to configurable CEL expressions. The v1.0.0 default already references `condition("Reconciled")` - **no update needed unless you have a custom config**.

**Action required (custom config only):** Replace all `condition("Ready")` with `condition("Reconciled")` in Sentinel and adapter CEL expressions. Adapter CEL lives under `preconditions` and `capture` blocks in the adapter Helm values - apply the same substitution.

```yaml
# v0.2.0 custom config (BROKEN in v1.0.0 - must update)
message_decision:
  params:
    - name: ref_time
      expr: 'condition("Ready").last_updated_time'    # WRONG: Returns zero-value
    - name: is_ready
      expr: 'condition("Ready").status == "True"'     # WRONG: Returns zero-value
  result: 'is_ready || ...'
```

```yaml
# v1.0.0 custom config (REQUIRED update)
message_decision:
  params:
    - name: ref_time
      expr: 'condition("Reconciled").last_updated_time'    # OK
    - name: is_reconciled
      expr: 'condition("Reconciled").status == "True"'     # OK
  result: 'is_reconciled || ...'
```

> `condition("Ready")` returns a zero-value condition in v1.0.0 (`status=""`, `observed_generation=0`). CEL expressions referencing it silently evaluate to false - Sentinel stops publishing events, adapters stop receiving work. No error is logged.
>
> **Pre-deploy check:** grep all custom config files for `condition("Ready")` and replace with `condition("Reconciled")`. If Sentinel stops publishing events after deployment, check CEL configuration first.

See [Sentinel Decision Engine Reference](https://github.com/openshift-hyperfleet/hyperfleet-sentinel/blob/main/docs/decision-engine.md).

### 1.3 JWT authentication required

**BREAKING.**

**Action required:** Set `config.server.jwt.enabled: true` and configure at least one issuer in v1.0.0 Helm values.

v1.0.0 removes OCM SDK ([§1.12](#112-ocm-sdk-removed)), making JWT the only auth mechanism. Helm defaults `jwt.enabled` to `false` for local development; production must enable it. Multiple issuers are supported - each with its own `identity_claim` ([§1.4](#14-jwt-identity-claim-for-audit-fields)):

```yaml
config:
  server:
    jwt:
      enabled: true
      configs:
        - issuer_url: https://accounts.google.com          # external IdP
          audience: hyperfleet-api
          identity_claim: email                             # claim for caller identity
        - issuer_url: https://kubernetes.default.svc.cluster.local  # K8s SA tokens
          audience: hyperfleet-api
          identity_claim: sub                               # K8s SA tokens use sub
          jwk_cert_url: https://kubernetes.default.svc.cluster.local/openid/v1/jwks
          jwk_cert_ca_file: /var/run/secrets/kubernetes.io/serviceaccount/ca.crt
```

> **If you don't act:** API accepts unauthenticated requests. No access control.
>
> **Startup crash:** `jwt.enabled: true` with an empty `configs: []` crashes the API with `"at least one issuer config is required"`. Always pair `enabled: true` with at least one issuer.
>
> **Key name:** The Helm values key is `configs` (matching the Go struct field). Do not use `issuers` - it is silently ignored by the Helm template, resulting in zero configured issuers and a startup crash.
>
> **Multi-issuer:** Each issuer entry needs its own `issuer_url` and `audience`. The K8s issuer also requires `jwk_cert_url` and typically `jwk_cert_ca_file` ([§1.15](#115-custom-ca-for-jwks-endpoint-tls)) because Go's default HTTP client does not trust the cluster CA.

### 1.4 JWT identity claim for audit fields

**BREAKING.**

**Action required:** Set `identity_claim` on each issuer entry under `configs`. For K8s SA tokens, use `sub` (`system:serviceaccount:<namespace>:<sa-name>`). For external IdPs, use `email` or `preferred_username` depending on your provider.

v0.2.0 hardcoded identity to `username`/`preferred_username`. v1.0.0 uses a configurable per-issuer claim that defaults to `email` if not set.

```yaml
config:
  server:
    jwt:
      configs:
        - issuer_url: https://accounts.google.com
          identity_claim: email     # external IdP
        - issuer_url: https://kubernetes.default.svc.cluster.local
          identity_claim: sub       # K8s SA tokens
```

> **Per-issuer setting:** `identity_claim` is configured on each issuer entry, not globally. Each issuer can use a different claim (e.g., `sub` for K8s SA tokens, `email` for external IdP). If omitted, defaults to `email`.
>
> **If you don't act:** All issuers default to `email`. Valid token missing the configured claim: mutating requests return `401`; GETs proceed without caller identity (no `created_by`/`updated_by` attribution). Verify your IdP tokens include the configured claim.

### 1.5 New entity types

Three new entity types for GCP partner integration: WifConfig, Channel, Version. Endpoints at [§2.3](#23-new-endpoints). Existing types included for reference. The `Required Adapters` column shows the Helm chart defaults:

| Kind | Parent | On Parent Delete | Required Adapters |
|------|--------|------------------|-------------------|
| `Cluster` | - | - | `validation`, `dns`, `pullsecret`, `hypershift` |
| `NodePool` | `Cluster` | `cascade` | `validation`, `hypershift` |
| `WifConfig` (new) | - | - | - |
| `Channel` (new) | - | - | - |
| `Version` (new) | `Channel` | `restrict` | - |

**No action required** with unmodified chart defaults. If you use custom Helm values overrides, preserve the `config.entities` list.

> **Entity configuration:** All entity types (including Cluster and NodePool) are now registered via the `config.entities` list in Helm values rather than hardcoded plugins. The Helm chart ships all five types pre-configured. If you use custom values overrides, preserve the `config.entities` list - an empty list produces an API with **zero entity endpoints** and no startup error. `required_adapters` controls which adapters must report `Available=True` for reconciliation and `Finalized=True` for hard-delete.

### 1.7 Sentinel Helm API client config path moved

**BREAKING.**

**Action required:** Move `config.hyperfleetApi.baseUrl` to `config.clients.hyperfleetApi.baseUrl` in Sentinel Helm values.

```yaml
# v0.2.0
config:
  hyperfleetApi:
    baseUrl: http://hyperfleet-api:8000

# v1.0.0
config:
  clients:
    hyperfleetApi:
      baseUrl: http://hyperfleet-api:8000
```

> **If you don't act:** Sentinel fails to start. Template renders empty base URL; validation fails with `clients.hyperfleet_api.base_url required`.

### 1.8 Sentinel Helm messageDecision params format changed

**BREAKING.**

**Action required:** Convert `messageDecision.params` from map to list-of-objects format.

```yaml
# v0.2.0 (map - BROKEN in v1.0.0)
messageDecision:
  params:
    ref_time: 'condition("Ready").last_updated_time'
    is_ready: 'condition("Ready").status == "True"'

# v1.0.0 (list)
messageDecision:
  params:
    - name: ref_time
      expr: 'condition("Reconciled").last_updated_time'
    - name: is_reconciled
      expr: 'condition("Reconciled").status == "True"'
```

> **If you don't act:** Helm template fails to render. Template iterates with `.name` and `.expr` fields; old map format has no such fields.

### 1.9 Sentinel config mount paths changed

**BREAKING.**

**Action required:** Update custom scripts, init containers, or sidecar configs to reference `/etc/hyperfleet/` instead of `/etc/sentinel/`.

- `/etc/sentinel/config.yaml` → `/etc/hyperfleet/config.yaml`
- `/etc/sentinel/broker.yaml` → `/etc/hyperfleet/broker.yaml`

> **If you don't act:** Custom scripts referencing old path fail with config not found.

### 1.10 Sentinel broker topic env var removed

**BREAKING.**

**Action required:** Set `broker.topic` in Helm values instead of the `BROKER_TOPIC` env var.

`BROKER_TOPIC` is no longer injected by the Sentinel deployment template.

> **If you don't act:** Topic override silently ignored, falling back to Helm value.

### 1.11 Adapter Helm broker type now required

**BREAKING.**

**Action required:** Set `broker.type` to `rabbitmq` or `googlepubsub` explicitly in adapter Helm values. For RabbitMQ, `url` and `exchange` are validated as required at Helm render time. `queue` and `exchangeType` are recommended but not enforced by the template.

```yaml
# RabbitMQ example
broker:
  type: rabbitmq
  rabbitmq:
    url: "amqp://user:pass@rabbitmq:5672/"
    queue: "hyperfleet-events"
    exchange: "hyperfleet"
    exchangeType: "topic"

# Google Pub/Sub example
broker:
  type: googlepubsub
  googlepubsub:
    projectId: "my-project"
    topic: "hyperfleet-events"
    subscriptionId: "adapter-sub"
```

> **If you don't act:** Helm rendering fails at template evaluation.

---

### 1.12 OCM SDK removed

**BREAKING.**

**Action required:** Remove OCM auth config (`server.acl`, `server.authz`) and switch to JWT config (`issuer_url`, `audience`, `identity_claim`).

OCM SDK removed; auth is now a standalone JWT handler. `server.acl` and `server.authz` were **removed from the API config schema**. In raw config files, including them triggers an `UnmarshalExact` startup error ([§4.3](#43-unknown-config-fields-cause-startup-errors)). In Helm deployments, these fields were never rendered by the template, so they are silently absent.

> **If you don't act:** In raw config files, API fails to start with an unknown-field error. In Helm deployments, old auth config is silently absent. Combined with [§1.3](#13-jwt-authentication-required) (`jwt.enabled` now `false`), the API starts with no authentication.

### 1.13 Default log format changed to JSON (Sentinel, Adapter)

**BREAKING.**

**Action required:** Update log parsing pipelines if they expect text format from Sentinel or Adapter.

Sentinel and Adapter `DefaultConfig()` changed from `FormatText` to `FormatJSON`. API was already JSON in v0.2.0 - unchanged.

> **If you don't act:** Log parsing breaks for Sentinel and Adapter output.

### 1.14 Sentinel and adapter API client JWT authentication

**BREAKING.**

**Action required:** Enable API client auth in Sentinel and adapter Helm values:

```yaml
config:
  clients:
    hyperfleetApi:
      auth:
        enabled: true
        audience: hyperfleet-api
        tokenPath: /var/run/secrets/hyperfleet/token
        expirationSeconds: 3600
        tokenCacheTtl: 30s
```

Mounts a projected Kubernetes `ServiceAccountToken` volume and injects a `Bearer` token into every API request. `audience` must match the API's JWT config. `tokenCacheTtl: 0` disables caching (re-reads the file on every request).

> **If you don't act:** Sentinel receives `401 Unauthorized` from the API. No CloudEvents published; adapters receive no work. Clusters stuck in pending.

### 1.15 Custom CA for JWKS endpoint TLS

**BREAKING.**

When using K8s SA tokens as JWT issuer, the API fetches JWKS from `https://kubernetes.default.svc.cluster.local/openid/v1/jwks`. Go's default HTTP client does not trust the cluster CA.

**Action required (when using K8s SA tokens as JWT issuer):** Set `jwk_cert_ca_file`:

```yaml
config:
  server:
    jwt:
      enabled: true
      configs:
        - issuer_url: https://kubernetes.default.svc.cluster.local
          jwk_cert_url: https://kubernetes.default.svc.cluster.local/openid/v1/jwks
          jwk_cert_ca_file: /var/run/secrets/kubernetes.io/serviceaccount/ca.crt
```

> **Constraint:** `jwk_cert_ca_file` requires `jwk_cert_url` to be set. Using it without `jwk_cert_url` is rejected at startup, regardless of whether `jwk_cert_file` is also configured. All three fields (`jwk_cert_url`, `jwk_cert_file`, `jwk_cert_ca_file`) may be set together - the CA file applies to the URL-based JWKS fetch.
>
> **If you don't act:** JWKS fetch fails with TLS certificate error. API rejects all authenticated requests.

## 2. API Contract

> API URI path remains `/api/hyperfleet/v1/...`. Component version bump does **not** change API version prefix. See [API Versioning](../../components/api-service/api-versioning.md).

### 2.1 Adapter status reporting POST to PUT

**BREAKING.**

**Action required:** Change adapter status reporting HTTP method from POST to PUT in adapter YAML configs.

Status reporting uses `PUT` with upsert semantics. `POST` returns `405 Method Not Allowed`.

```bash
# v0.2.0
curl -X POST "${API_URL}/api/hyperfleet/v1/clusters/${CLUSTER_ID}/statuses" \
  -H "Content-Type: application/json" -d @status.json

# v1.0.0
curl -X PUT "${API_URL}/api/hyperfleet/v1/clusters/${CLUSTER_ID}/statuses" \
  -H "Content-Type: application/json" -d @status.json
```

Method-only change - request body (`AdapterStatusCreateRequest`) is unchanged. `Finalized` ([§3.2](#32-finalized-condition-for-deletion-flows)) is a new condition type value, not a schema change. `reason` and `message` on conditions are now optional ([§2.6](#26-condition-reason-and-message-now-optional)).

See [Adapter Status Contract](../../components/adapter/framework/adapter-status-contract.md).

---

### 2.2 Unified `Resource` model for all entity types

All entity types now use the generic `Resource` type internally. The `clusters` and `node_pools` tables are replaced by a single `resources` table with labels in `resource_labels`.

**API endpoints and request/response shapes are unchanged** - `/api/hyperfleet/v1/clusters`, `/api/hyperfleet/v1/clusters/{id}/nodepools`, and all existing paths work with identical payloads. `kind` in individual responses distinguishes entity types. Entity types are registered via `config.entities` in Helm values (each entry is an `EntityDescriptor`).

**No action required** for existing Cluster/NodePool API consumers.

### 2.3 New endpoints

| Endpoint | Description |
|----------|-------------|
| `GET/POST /api/hyperfleet/v1/wifconfigs` | WIF configuration resources (CRUD) |
| `GET/POST /api/hyperfleet/v1/channels` | Release channel resources (CRUD) |
| `GET/POST /api/hyperfleet/v1/channels/{parent_id}/versions` | Versions nested under channels (CRUD) |
| `POST /api/hyperfleet/v1/clusters/{id}/force-delete` | Force-delete stuck cluster |
| `POST /api/hyperfleet/v1/clusters/{id}/nodepools/{np_id}/force-delete` | Force-delete stuck node pool |
| `DELETE /api/hyperfleet/v1/clusters/{id}/nodepools/{np_id}` | Soft-delete node pool (new) |
| `PATCH /api/hyperfleet/v1/clusters/{id}/nodepools/{np_id}` | Patch node pool (new) |

**No action required** - additive endpoints.

> **Force-delete:** Clusters and node pools only. Requires `Finalizing` state (`deleted_time` set). Destructive admin operation - restrict via RBAC. See [Force Deletion Design](../force-deletion-design.md).

### 2.4 Delete returns 202 Accepted

**BREAKING.**

**Action required:** Audit all DELETE call sites - calls that previously expected 501 will now succeed and may cascade-delete child resources.

v0.2.0 DELETE returned `501 Not Implemented`. v1.0.0 implements two-phase delete:

1. **Soft delete:** Sets `deleted_time`, increments `generation`. Returns `202 Accepted`.
2. **Hard delete:** When all required adapters report `Finalized=True`, records are removed.

> **If you don't act:** Code that ignored 501 errors will now trigger real deletions.
>
> **Data-loss warning:** Deleting a Cluster always cascade-deletes all NodePools. No per-request override.

---

### 2.5 kind field removed from list responses

**BREAKING.**

**Action required:** Update client code that expects `kind` in list response envelopes.

`kind` removed from `ClusterList`, `NodePoolList`, `ResourceList`, and `AdapterStatusList`. Individual resource responses still include `kind`.

```json
// v0.2.0 list envelope (kind present)
{
  "kind": "ClusterList",
  "items": [
    { "id": "abc-123", "kind": "Cluster", "name": "prod-1", ... }
  ],
  "page": 1, "size": 20, "total": 1
}

// v1.0.0 list envelope (kind removed - items still carry kind)
{
  "items": [
    { "id": "abc-123", "kind": "Cluster", "name": "prod-1", ... }
  ],
  "page": 1, "size": 20, "total": 1
}
```

> **If you don't act:** Parse error if client schema requires `kind` on list responses.

---

### 2.6 Condition reason and message now optional

`reason` and `message` on adapter conditions are optional. Still recommended for observability.

**No action required.**

### 2.7 Pagination query parameters renamed

**BREAKING.**

**Action required:** Replace `pageSize` with `size` and `orderBy` with `order` in all list-endpoint calls (`GET /clusters`, `GET /nodepools`, `GET /resources`). Regenerate any clients generated from the OpenAPI spec.

```bash
# v0.2.0
curl "${API_URL}/api/hyperfleet/v1/clusters?pageSize=50&orderBy=name"

# v1.0.0
curl "${API_URL}/api/hyperfleet/v1/clusters?size=50&order=name"
```

> **If you don't act:** Old parameter names are silently ignored. Requests fall back to defaults (page 1, size 20, no ordering) with no error returned.

---

### 2.8 Error detail field now optional

`detail` in RFC 9457 error responses changed from required to optional, aligning with TypeSpec (`detail?: string`) and RFC 9457 Section 3.1. All HyperFleet implementations still populate `detail` in practice.

**No action required** unless client code treats a missing `detail` field as a parse error.

## 3. Statuses Contract

### 3.1 Aggregated condition renames

**BREAKING.**

**Action required:** Replace `Ready` with `Reconciled` and `Available` with `LastKnownReconciled` in resource-level condition lookups.

| v0.2.0 | v1.0.0 | Meaning |
|--------|--------|---------|
| `Ready` | `Reconciled` | All required adapters report `Available=True` at current generation |
| `Available` | `LastKnownReconciled` | Sticky - stays `True` across generation bumps until new reconciliation completes |

Adapter-level conditions (`Applied`, `Available`, `Health`) are **unchanged**.

> **Name collision:** Adapter-level `Available` still exists as a per-adapter condition. Resource-level `Available` is now `LastKnownReconciled`. Scope condition lookups to the correct level.
>
> **If you don't act:** Reading `Ready` / `Available` from resource conditions returns nil/empty.

See [ADR-0007](../../adrs/0007-conditions-based-status-model.md) (Evolution section).

---

### 3.2 Finalized condition for deletion flows

**BREAKING.**

**Action required:** Adapters must report `Finalized=True` after cleanup, or resources remain stuck in `Finalizing`.

Include `{ "type": "Finalized", "status": "True", "reason": "CleanupComplete" }` in the adapter status conditions array after cleanup. API gates hard-delete on all required adapters reporting `Finalized=True`.

> **If you don't act:** Resources stuck in `Finalizing` indefinitely. Use `POST /{id}/force-delete` to clear.

---

### 3.3-3.5 Other status changes (no action required)

- **True/False only in steady state.** Resource-level conditions enforce True/False. `Unknown` may appear transiently before the first adapter report.
- **Mapped conditions.** Resource `status.conditions` may contain dynamically-created conditions from adapter conditions via CEL rules ([Condition Mapping Design](../../components/api-service/condition-mapping-design.md)).
- **Non-reconcilable resources.** WifConfig, Channel, Version have no `RequiredAdapters` - no `Reconciled`/`LastKnownReconciled` conditions. Only Cluster and NodePool receive aggregated conditions.

## 4. Operating Model

### 4.1 Fresh database

**BREAKING.**

**Action required:** Deploy with a fresh, empty database. Do not reuse v0.2.0 database. Re-register all resources via API after deployment.

The `clusters` and `node_pools` tables no longer exist; all entity types are stored in a unified `resources` table with labels in `resource_labels` and conditions in `resource_conditions`. The condition rename from `Ready` to `Reconciled` ([§3.1](#31-aggregated-condition-renames)) also applies. Nothing is migrated from v0.2.0.

> **If you don't act:** Undefined behavior against old schema.

---

### 4.2 Cascade delete on child resources

**BREAKING.**

New in v1.0.0. In v0.2.0, DELETE returned `501 Not Implemented` - no cascade existed.

Policies per entity type, not configurable:

- **NodePool** → `cascade`: deleting Cluster cascade-deletes all NodePools
- **Version** → `restrict`: deleting Channel blocked while Versions exist

```bash
curl -X DELETE "${API_URL}/api/hyperfleet/v1/clusters/${ID}"
# Cascade-deletes all NodePools automatically
# Returns 409 if restrict-policy children exist
```

> **If you don't act:** Deleting Cluster silently cascade-deletes all NodePools. No per-request opt-out.

---

### 4.3 Unknown config fields cause startup errors

**BREAKING.**

**Action required:** Remove v0.2.0-only properties from Sentinel configs (e.g., `messaging_system`). Test config against v1.0.0 binary before deploying.

Unexpected properties trigger a startup error. The API already enforced this in v0.2.0 (`UnmarshalExact`). New in v1.0.0: **Sentinel also moved to strict parsing** - v0.2.0 Sentinel used permissive `Unmarshal` which silently accepted unknown fields.

> **If you don't act:** Sentinel refuses to start, naming the unexpected field. API behavior unchanged (was already strict).

---

### 4.4 PgBouncer sidecar replaced by generic sidecars

**BREAKING.**

**Action required:** Rewrite PgBouncer config as a generic `sidecars` list entry in the API Helm values.

The `database.pgbouncer.*` Helm values tree was removed. Configure PgBouncer as a standard container spec in `sidecars`:

```yaml
# v0.2.0 (REMOVED - silently ignored in v1.0.0)
database:
  pgbouncer:
    enabled: true
    port: 6432
    poolMode: transaction

# v1.0.0 - generic sidecar entry
sidecars:
  - name: pgbouncer
    image: public.ecr.aws/bitnami/pgbouncer:1.25.1
    securityContext:
      allowPrivilegeEscalation: false
      capabilities:
        drop: [ALL]
      readOnlyRootFilesystem: true
      seccompProfile:
        type: RuntimeDefault
    ports:
      - name: pgbouncer
        containerPort: 6432
        protocol: TCP
    env:
      - name: POSTGRESQL_HOST
        value: my-postgresql-host
      - name: POSTGRESQL_PORT
        value: "5432"
      - name: POSTGRESQL_DATABASE
        value: hyperfleet
      - name: POSTGRESQL_USERNAME
        value: hyperfleet
      - name: POSTGRESQL_PASSWORD
        valueFrom:
          secretKeyRef:
            name: my-db-secret
            key: db.password
      - name: PGBOUNCER_PORT
        value: "6432"
      - name: PGBOUNCER_POOL_MODE
        value: transaction
    resources:
      limits:
        cpu: 200m
        memory: 128Mi
      requests:
        cpu: 50m
        memory: 64Mi
```

For proxies needed during init container execution (e.g., `db-migrate`), use `nativeSidecars` instead. Native sidecars (Kubernetes 1.28+) are init containers with `restartPolicy: Always` that start before other init containers.

> **If you don't act:** Old `database.pgbouncer.*` values silently ignored. Pod starts without DB proxy sidecar.
